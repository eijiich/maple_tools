# Gear Progression

Ranks every available gear upgrade by **meso per point of main-stat-equivalent**, so the next purchase
is the one that actually buys the most damage. Reboot economics: meso is the only currency,
SSF assumed always on. Flames appear on both: the main ranking can price them off the flat-meso
bonus-stat reset (behind a toggle, off by default while that patch is unreleased), and a second
table ranks flames you already own by how likely a reroll is to help — a different question, on a
different denominator.

Open `index.html` directly. No server, no build step, no runtime dependencies — the scripts
are plain `<script src>` tags precisely so `file://` works (ES modules would be CORS-blocked).

**Or open `gear-progression-standalone.html`, which is the whole tool in one file** — every
script inlined, no `js/` folder needed, so it survives being emailed or dropped on a phone.
`selftest-standalone.html` is the same treatment for the checks, so a single file can still be
verified. Both are **generated** from the multi-file version; edit `js/*.js` and regenerate:

```
python tools/build_single.py
```

Note that localStorage is keyed per origin *and* path, so the standalone file has its own
saved state, separate from `index.html`. Use export/import to move between them.

  cubing.js              port of backend/maple_cubing/cubing.py + target scanner

`reference/` is where the authority lives. Nothing here invents game data:

| `Star Force Enhancement_Stat Tables … .htm` | per-star stat gain by level bracket |

| `MathBro's Cubing Calculator.htm` | per-cube reveal fee (`_files/cubes_CDdL.js`); independent confirmation of the hat pool fix |

| `Flame Calculator _ whackybeanz.htm` | minified Next.js — output cross-check only, not a data source |

Plus `../backend/maple_cubing/cubing.py` for the cube line pools.

Two traps in that folder, both handled, worth knowing if you re-derive anything:

- **`worker.js` was not captured by "Save page as"** — it loads via `new Worker()`, not a
  `<script src>`, so it was downloaded separately. It is also the authoritative copy: it
  disagrees with the page's own `main_IRbm.js` on abyssal/`reincarnation` tier odds
  (`4:0.01 / 7:0.02` versus `4:0 / 7:0.03`). `worker.js` is what actually computes.
- **MathBro's cubing tables are a 2023 snapshot** (`Auto-generated on 11/14/2023`) and cap
  stat lines at 12%. They predate the lv160+ bump, which is why that came from StrategyWiki.

## Running things

```
python tools/check_js.py                  # do this first; needs `pip install quickjs`
python tools/build_single.py              # regenerate the standalone single-file builds
python tools/extract_sf_stats.py          # rebuild js/sf-stats.js
python tools/extract_sf_stats.py --dump   # inspect parsed cells, write nothing
python tools/verify_cubing.py             # parity vs cubing.py; exit 0 = clean
python tools/verify_pipeline.py           # oracle checks + sample rankings
```

Three layers, catching different things — run all three:

- `check_js.py` is the one command that covers both layers. It parses every file, loads the
  bundle against a stub DOM, runs the initial render, asserts the tables have rows and that
  every row matches its header's column count (**derived from `index.html`'s own `<thead>`** —
  a hardcoded count went stale the moment a column was dropped), **and runs `selftest.html`'s
  script the way the browser does: engine files only, no `app.js`.**
- That last part matters. `selftest.html` deliberately does not load `app.js`, so a check there
  reaching for an `app.js` symbol throws at load and silently skips every later check. It caught
  three of mine (`weightsProfileText`, `WEAPON_KINDS`, `LEVELS`) only after the fact. Now the
  failure is immediate, and the fix is either to move the symbol into an engine file where it
  belongs or to assert it in `check_js.py`, where `app.js` *is* loaded.
- **`check_js.py` also asserts, statically, that every id `app.js` looks up exists in
  `index.html` *above* the `<script>` tags.** The stub DOM's `getElementById` fabricates any id
  it is asked for, so a missing element can never throw there — and that is exactly how a
  compare panel appended *after* the scripts shipped: `app.js` ran first, got `null` from the
  real DOM, and the whole page died on one `addEventListener`. All checks were green. The check
  was verified by putting the bug back: it reports all six ids as `declared AFTER the scripts`.
- `selftest.html` still opens standalone in a real browser over `file://`.
- **The single-file builds are checked two ways**, because "matches the generator" and "works"
  are different claims. `check_js.py` rebuilds them in memory and fails if what's on disk has
  drifted, *then* runs the scripts extracted from the file on disk — 23 gear rows for the tool,
  453 checks for the selftest. A stale standalone file is the dangerous kind of wrong: it still
  opens, still renders, and quietly ranks with last week's engine.
- The Python mirrors verify the *maths* independently of the JS.

## Things worth knowing before trusting a number

- **`cubing.py` had a bug, now fixed in both places.** Its `hat_unique_prob` set `Zero` to
  41/52, making that pool sum to 1.077 — the only one of 22 that wasn't 1. It must be 37/52
  (5+4+6+37 = 52, matching `bottom` and `shoes`), which MathBro's rate tables confirm
  independently. Left alone it priced hat targets ~6% cheap. **Fixed in both `cubing.js` and
  `cubing.py`**, with the reasoning inline in each.
- **The ranking prices the mode policy you picked, not the cheapest one.** Stars 15★→22★ each
  take a mode 1–4 in *Star force settings*, with the three strategies people name as presets:
  `111/11/11` (cheapest expected meso, most booms), `444/11/44` (safeguard the ends, ride
  18★→20★), `444/44/44` (cannot boom below 22★). Once you name a strategy its cost is not a
  search, so `sfPolicy`/`solve` replaced `solveUnconstrained` on this path. At lv150 15★→22★:
  6.58b / 12.19b / 29.78b mean, and 3.82 / 0.79 / 0.00 booms.
- **This replaced a per-row `Safe` checkbox**, which could only say all-or-nothing and — being
  `solveSpares` with one item — read "impossible" for every row above 21★. That is a true answer
  to "guarantee arrival with one item" and a useless one to ask per row. `solveUnconstrained` and
  `solveSpares` are still in `sf.js` as vendored reference and as oracles the self-tests check
  the policy numbers against: no fixed policy may beat the optimum, and `111/11/11` matches it
  exactly when spares are free.
- **Star force strategy is per slot, written as text.** The gear table's **Plan** column takes
  `444/11/44` (or `4441144`, or `4-4-4-1-1-4-4`); blank uses the global strategy, shown greyed as
  the placeholder. A text field rather than seven dropdowns per row because 23 slots × 7 stars is
  not a table anyone can read, and because that is how players say it anyway. An unparseable
  entry falls back to the global rather than to all-mode-1, so a half-typed `44` doesn't silently
  reprice mid-keystroke.
- **Mode changes propagate backwards, never forwards.** `X[s]` depends on the modes at `s` and at
  every star from `recoveryStar(s)` up. So safeguarding 17★→18★ *does* change 18★→19★ — a boom at
  18★ drops to **12★**, and the recovery climb re-walks 17★→18★ under whatever mode is set. A mode
  set at 20★ cannot touch 18★→19★. Both directions are asserted; the first caught a wrong
  assumption of mine that the steps were independent.
- **Mode labels quote the rate you actually face.** `4.72% boom (×1)` at 17★, with the event's
  reduction already applied, so they move when the event changes and the panel re-renders with it.
- **Genesis and Destiny weapons can't be star forced.** Both arrive at a fixed 22★, the stars
  coming from liberation quests rather than meso, so weapon star force is dropped from the
  ranking entirely — the row says why instead of vanishing, which would read as "already maxed".
  Two mutually exclusive checkboxes in *Star force settings*, stored as one `weaponKind` field
  so both-on is unrepresentable rather than something to keep in sync. Stored **per character**,
  since the weapon belongs to the character even though that panel is otherwise global.
- **Second-stage Destiny liberation unlocks 22★→25★, and a boom there is not just a fee.**
  Per the user (namu.wiki's Destiny weapon page — the site 403s automated fetches, so these are
  their figures): 10b revives the weapon but only to **12★**; from there 54.2b buys a guaranteed
  22★, or you re-star-force 12★→22★ yourself. Recovery is therefore a **choice**, and the
  cheaper route in expectation is what a boom costs. At lv250 buying back wins under every
  preset — 54.2b against 65.5b to re-climb under `444/11/44` — but by only ~11b, close enough
  that both are priced every time rather than assumed.
- **An earlier version of this was wrong, and badly.** It assumed the weapon came back at 22★
  for the 10b alone, which understated the climb **5.7×** (164b against the correct 930b for
  lv250 22★→25★). That was the one number here never taken from a source, flagged as such at
  the time, and the correction came from the user's own testing.
- **A Destiny is dearer than an ordinary lv250 weapon, but only ~1.26× at p85**, which is not
  obvious. The ordinary one *booms more* — 23.4 against 14.1, since it falls to 17★/19★ and
  re-climbs through the boom-prone stars — while each Destiny boom costs a flat 64.2b. Fewer,
  pricier booms.
- **Fees are reported separately from re-climb spend.** The row says "612.72b of that in fees",
  counting only meso handed over (revive, plus the guarantee if bought). The re-climb portion is
  star force spend already inside the total, so attributing it again produced a component
  *larger than the whole* — 474b of a 232b step — until it was split out. Fees run ~98% of a
  Destiny step.
- **The spares warning is suppressed for a Destiny.** There is one weapon and you pay to get it
  back; nothing is consumed from a stack, so a spares count says nothing about it.
- **The rows dropdown is persisted, and the control is written from state on every render.**
  Browsers restore `<select>` values across a reload, so a default living only in JS drifted from
  the control the moment you changed it and came back — the dropdown read 10 while the table
  still paged by 50. State is the single source of truth now.
- **Paging controls sit above the table.** Below it they moved whenever a short last page changed
  the table's height, sliding the button out from under the cursor.
- **`Spares` never changes the ranked cost.** It only drives the "you'll run out" warning.
  Counterintuitive, but the ranking is unconstrained by design.
- **lv130 caps at 20★, and that came free.** Some accessories and secondaries sit at lv130.
  It falls in the wiki's first bracket, `128-137`, whose tables simply stop at 20★ — so
  `SF_CAP_ARMOR[0]` and `SF_CAP_WEAPON[0]` were already 20 and `sfCap` needed no special case.
  Milestones above the cap filter themselves out, leaving `15, 17, 18`. Adding `130` to the
  level dropdown was the whole change. Flames scale with it correctly (expected 39.56 at lv130
  against 40.71 at lv140/150, which share a flame bracket) and cube reveal is 20×130² = 338k.
- **Armor gains attack from 16★ up**, and for a mage that attack is ~⅔ of the value of a
  lv150 star. From 23★ up the gain is attack *only* — no class stat at all.
- **`Class Stat +N` is per class-relevant stat**, not a total, so it is multiplied by the sum
  of the flat stat weights (1 + 0.1 = 1.1 for a mage).
- **Main-stat% and all-stat% are scored as one currency.** All-stat is strictly worth a shade
  more (it lifts the secondary stat too), but scoring that gap made the scan offer lateral
  30%→30% rerolls, and rank 27% all-stat *above* 30% main-stat. Any composition summing to the
  same percentage now scores identically.
- **Classes fall out of the weights — there is no class picker.** Xenon, Shadower, DB and
  Cadena flames work automatically: every stat and combo slot is valued per-stat from the
  paste, and the tracked/junk splits land exactly on MathBro's per-class `choose_from`
  constants (10 / 8 / 8) by construction. Demon Avenger: flat-HP flame lines are valued by
  the paste's HP weight — the HP column appears only when that weight is nonzero — and HP%
  potentials price via the HP% weight, both matching `worker.js:871` where HP *is* DA's
  score. Two conditionals: the main/all-stat collapse switches off when All Stat% exceeds
  1.6× a single stat% (Xenon values it at roughly triple; a Demon Avenger's All Stat% comes out
  *exactly equal* to its STR%, which is the correct confirmation — a DA gains from STR alone, so
  all-stat buys it nothing extra), and sub-stat % lines are lifted
  out of the cube pools' Zero once they're worth ≥25% of the main stat's % weight (Xenon
  yes; a mage's LUK% and a Shadower's DEX%/STR% stay folded — their bases are too small for
  the % lines to matter even though the flat stats matter for flames). Kanna post-rework is
  a standard mage. Known DA gap: sub-16★ star force grants flat HP the stat tables drop,
  so DA star force reads slightly low.
- **lv160+ adds `+1` to every numeric potential % line.** The wiki words it as `151+`; no
  equipment exists between 151 and 159, so in practice it is the 160+ rule. Lines whose value
  sits in the line name — IED 30/35/40, Boss 30/35/40, cooldown — do not scale. The bump is
  applied **per line**, leaving the odds untouched, which is why P(33% on a 160 item) is
  bit-for-bit P(30% on a 150 one). The wiki page is a snapshot; if the system changes, re-save
  it and adjust `CUBE_LEVEL_BUMP`.
- **The percentile moves the booms too, not just the cost.** The detail column quoted expected
  booms even at p85, which read as though a percentile only touched the cost — but a climb is
  expensive *because* it boomed more. The figure is lostara's own: a lognormal fitted to the mean
  and `DVar`, reported continuously, exactly its line 1312. Verified to the second decimal against
  lostara for 22★→23★ under `444/11/44` with ssf — **1.91 expected, 3.26 at p85**.
- **`DVar` had never been validated** before this went in. It is within 0.4% of Monte Carlo, and
  two of its values are pinned in the self-tests as regression anchors.
- **A discrete quantile is a ceiling, which is why not to use one here.** I first fitted a
  negative binomial and returned an integer — the right family for a count, and it matched
  simulated quantiles exactly, but a discrete quantile is the smallest integer whose CDF reaches
  the target, i.e. `ceil` of the continuous figure. So 22★→23★ read **4** where lostara says 3.26.
  This engine exists to agree with lostara, and `3.26` also carries "about three, maybe four" in a
  way a hard 4 does not. That removed ~40 lines, including a large-mean branch I got wrong twice
  (first returning a loop cap as data, then a normal fit that misplaced the median by 44%).
- **Booms don't depend on item level**, only cost does — rates are level-independent — so the same
  boom figures come out at lv150 and lv250. Asserted, since it is an easy thing to break.
- **The strategy drives the boom count even above 21★**, where no mode choice exists. A boom at
  22★ falls to **17★**, and the re-climb runs 15★–21★ where the modes do apply: 22★→23★ expects
  1.91 booms under `444/11/44` but 5.05 under `111/11/11`. If a figure looks wrong, check the plan
  before the maths.
- **Cooldown is a constraint, not a score.** There is no seconds-to-stat exchange rate. Asking
  for −2s filters the roll space, which pins a line and drops the reachable ceiling from three
  stat lines to two. Judging whether that trade is worth it is yours.
- **Cube sales take 25% off the cube, not off the reveal fee.** They are separate charges and
  the sale is on the cube, so a discounted red cube is `12m × 0.75 + 20×level²`. That floors the
  real saving below 25% — a lv150 hat target goes 28.8m → 21.8m, about 24%. One toggle in *Star
  force settings*, alongside the other event switches. `CUBE_SALE_OFF` is the one line to change
  if a sale ever discounts the reveal too.
- **Gloves offer Crit DMG first.** They are the only slot that rolls it and it beats the stat
  lines there, so it leads the picker via `CUBE_LINE_ORDER_BY_CATEGORY` rather than sitting
  below three stat entries. Ordering only — the pool, the odds and the scoring are untouched,
  and every other category still leads with its stat line. Asserted both ways.
- **The pendants have a swap button**, a dim `⇅` in Pendant 1's Slot cell. It exchanges the two
  slots outright — level, stars, potential and flames — because those are the one genuinely
  interchangeable pair, and swapping only some fields would leave a row describing an item that
  doesn't exist. Both tables read the same slot objects, so one swap moves the flame rows too.
- **Line 1 is always prime, so its picker only offers legendary-tier values.**
  `CUBE_PRIME_PROB[*][0]` is `1.0` for both cube types and `cubeLineDists` builds slot 1 from the
  legendary pool alone — so a 9% main stat cannot *be* line 1, only 12% can. The picker used to
  merge both pools for all three lines, which let you describe an item the engine treats as
  impossible. On a hat that drops `main_stats 9`, `all_stats 6` and `HP 9`; on a weapon
  `ATT 10`, `BOSS 30`, `IED 30`. The maths never included them, so no probability changed. A
  value already saved that the filter would drop is still listed, tagged `(not prime)`, so an
  older save reads back as what it actually holds rather than silently appearing to be something
  else.
- **Both cube types are always scanned.** Line 1 is prime for either cube, so easy targets
  cost red's 12m rather than black's 22m; black only wins where two or three prime lines are
  needed. Each rung names its cube.
- **Revealing potential costs `20 × level²` per cube** on top of the cube itself — 450k at
  lv150, 1.25m at lv250. `cubing.py` omits this.
- **IED is valued linearly** in the line's stated percent, though it really stacks as
  1−(1−a)(1−b). An item carrying two IED lines is therefore somewhat overvalued.
- **Secondaries use the ARMOR stat table.** Settled by measurement, not inference: a lv200
  secondary at 20★ has cumulative **+115 stat and +70 attack**, which is the armor table exactly.
  The weapon table happens to give the same 115 stat, so it is the flat 70 attack that decides
  it — weapons compute attack as a formula over their own base instead. That retired
  `sf-stats-secondary.js`, its `SF_CAP_SECONDARY` zeros, the `sfTableEmpty` guard it existed for,
  the `Tbl` per-row override, and `SECONDARY-TABLE-HOWTO.md`. A control whose only correct
  setting is the default is just a way to get the wrong answer.
- **Most secondaries still aren't star forceable**, so the row defaults to SF off — that is now a
  sensible default rather than a missing-data guard. The ones that can be forced are the lv130
  shields for explorer mages, thieves and warriors, which cap at 20★ from the `128-137` bracket.
  Kanna and Dual Blade are exceptions, deliberately out of scope.
- **An Astra secondary buys its spares at 1b each.** That is exactly what `itemCost` means, so a
  boom there is priced instead of free. It sits beside the weapon toggles but drives a *separate*
  field, because a secondary rule is not exclusive with a weapon rule — you can hold a Destiny and
  an Astra at once, and only the two weapon boxes exclude each other. A lv130 shield 15★→20★ goes
  2.02b → 3.56b with it on. With a fully guarded plan nothing booms, so the 1b never applies;
  asserted.
- **The flame axis is behind a toggle, off by default.** The meso reset is a patch note, not a
  release, so the shipped default reproduces the pre-patch ranking exactly — asserted by
  fingerprinting every non-flame row with the flag on and off and requiring them equal. One flag
  (`state.flameReset`), surfaced as a button in both the ranking bar and the compare bar, because
  it answers one question — "does this exist on my server yet" — and two independent flags could
  disagree. It is part of `compareGlobalSig`, so flipping it makes the compare tab report itself
  stale rather than show numbers computed under the other policy.
- **`stat()` keeps about three significant figures.** One fixed decimal suited a stat paste
  (values 10–500) and wrecked a Final Damage paste (values 0.05–2): every flame gain in the
  ranking read `0.1`, one read `0.0`, while the meso/%fd column beside them differed by 20%.
  The precision was always computed; it was discarded at display.
- **The flames table has a "Flame score" column**: the flame in main-stat points, the number
  people quote. In a stat paste it equals **Now**; in a %fd paste it is Now divided by the main
  stat's own %fd-per-point weight (HP's for a Demon Avenger). Asserted unit-invariant: scaling
  every weight in the paste by 0.01 and marking it %fd shrinks Now 100× and leaves the score
  exactly where it was.
- **Flame-reset detail quotes the median reset count beside the mean.** A geometric mean sits
  far above its median once p is small — at 0.4% per reset the mean is 270 and the median 187 —
  so "270 expected" read as "about 270" errs toward optimism. Both are shown.
- **Flames are ranked twice, deliberately.** Bonus stats can be reset for a flat
  **3,000,000 mesos**, which gives a flame a meso price and lets it into the main ranking
  as a third axis beside star force and cubing. The separate flames table stays, unpriced,
  because it answers a different question: which slot a flame *you already own* is least likely
  to be wasted on.
- **The flame axis's meso-per-point is `3m ÷ E[gain per reset]`.** A row means "reset until it
  beats what the item has, then keep it" — the patch lets you decline the new roll, so a bad
  reset costs only the mesos, which is exactly the `E[max(0, new − now)]` `flameReroll` already
  models. Both the cost and the gain scale with the number of resets and the scaling cancels
  (`cost = price/p`, `gain = gainPerRoll/p`), so the ratio depends only on what one reset adds
  on average. `rollsToBeat` still sets the **Est. cost** column, since that is the meso actually
  consumed. Asserted both ways in `check_js.py`.
- **The meso reset always rates at the Black Rebirth (`eternal`) table**, per the patch note's
  "the reset rates are identical to Black Rebirth Flames" — *not* whichever flame the slot's own
  picker is set to. Changing that picker must not move the ranking row, and a test pins it.
  Flame *advantage* does still come from the slot: it is a property of the item and class
  pairing, not of the flame item being consumed.
- **Flames have their own percentile box**, separate from the ranking's. The confidence you want
  for "will a reroll beat what I have" is not the confidence you want for "how much meso should I
  set aside". It drives **Rolls to beat**, and unlike star force the figure is exact rather than
  fitted — reroll counts are geometric, so `geometricPct` is closed-form.
- **A geometric pXX is not always above the mean.** When an improvement is near-certain the mean
  is the higher number, because the tail is what pulls it up: at p=0.95 the mean is 1.053 resets
  and the 85th percentile is 1. An unflamed item sits exactly there, so the flame tests pin both
  directions rather than assuming the usual one.
- **Flameable slots are armour, weapon, accessories, pocket and medal.** Not secondary, not
  emblem, not rings — all three confirmed, not assumed. There are only **two** bonus-stat
  pools, weapon (21 slots) and everything else (19); level scales the values, not the pool.
  So accessories, pocket and medal correctly share armour's pool.
- **Damage% *is* boss damage%** — one weight, boss simply counting 2 per flame tier to
  damage's 1. Boss% applies only to bosses, which is all this tool optimises for. MathBro
  agrees: `worker.js:755` multiplies both by a single shared `stat_equivalences.dmg`.
- **MapleScouter's table is three columns, and the middle one matters.** Row label, an
  editable **amount**, then the value of that amount — and the value column is a dropdown:
  *Main Stat* gives main-stat-equivalent, *Final Damage* gives % of final damage with a `%` on
  every row. Both are the same weight set in different units and rank identically; only the
  printed scale differs. The `%` has nothing to do with class.
- **Both value columns are per-*line*, so the amounts are divided back out.** The engines apply
  their own amounts (a 12% potential line, a tier-7 flame), so feeding totals in counts each row
  twice over — 12× for a 12% line, 9× for a 9% one. Different factor per row, so it **reorders**
  the ranking rather than just inflating it. The amount column doesn't survive select-and-copy,
  hence the inputs under the paste box: type what your page shows, or hit **MapleScouter
  defaults** if you never edited them. Blank means 1, i.e. already per point, which is why an
  older save ranks exactly as it did. A paste that *does* carry three columns fills them in
  itself and locks them. Verified: pasting either column with defaults filled gives byte-identical
  50-row ordering to the per-point figures, and `Main Stat ÷ amount` reproduces those figures
  exactly — including `HP 30/30 = 1`.
- **`suspectTotals` only guards the Main Stat column.** It fires when no row lands on 1 *and*
  nothing is below 1, then clears itself once the amounts bring a row back to 1. Both signals
  are needed, since a genuine per-point paste always has small rows (`Not Affected by %` sits
  near 0.1) — one coincidence shouldn't scold you. **Known gap:** an undivided *Final Damage*
  paste can't be caught this way. That column normalises nothing and its rows are all sub-1
  already, so there's no signal to read; it's excluded rather than false-flagged. Check the
  profile line says `N rows divided by` when you expect it to.
- **MapleScouter weights are derivatives** at your current gear, not constants. Re-paste after
  any significant change.

Every table column is left-aligned. Mixing right-aligned numerics with left-aligned text down
a single row reads as accidental; `font-variant-numeric: tabular-nums` keeps digits lining up
without needing right alignment to do it.

## Comparing characters

Second tab, not a second page. Both panes live inside `div.wrap`, which carries the
`max-width` and padding — the compare tab was briefly outside it and rendered wider than the
header and every other panel. `/compare/` would need the engines loaded twice, would break
the single-file build — that is one HTML file by definition — and would lean on the two paths
sharing localStorage: true on an http origin, browser-dependent from `file://`. One document
means one state object, so there is nothing to sync. The active tab is persisted.

Switching to the tab is instant (0.5 ms) and deliberately does **not** compute: opening a tab
should never freeze the page for seconds. The table asks for recalculate.

It merges the ranking and the flame list across two or more characters, so
"which of my characters gets the most from the next 50b" is one table. Untick anyone you
aren't improving right now.

Two things about the units, because one is exact and the other is a judgement call:

- **Rolls to beat compares exactly.** It comes from a probability, and probability is
  scale-invariant — multiply a character's weights by any constant and both the current
  flame's value and every rolled outcome scale together, so "will a reroll beat this" is
  unchanged. Sorted fewest-rolls-first, i.e. easiest wins at the top.
- **Meso per stat is each character's own main stat point**, since MapleScouter normalises
  every paste to 1. It ranks who buys a stat point cheapest, which is the right question
  when a point is worth about the same to each of them — true at similar progression. It
  drifts if their totals differ a lot, because then one point is a different share of their
  damage. Kept deliberately: the alternative needs a hand-entered total main stat per
  character, and the comparison is useful without it. If two selected pastes use *different*
  MapleScouter value columns, that is a harder error and the panel says so instead of ranking.

**Cached per character**, against a signature of everything that changes the answer. So the
cheap operations are cheap and only real work costs anything:

| | |
|---|---|
| untick a character | free — filters the cache |
| switch tabs | free |
| re-tick one already computed | free |
| tick a character never computed | that character alone |
| edit one character | invalidates that character alone |
| change a global setting | invalidates all of them |

The first version used one counter bumped by `save()`, which meant **unticking a character —
and even switching tabs — blanked the whole table**: both call `save()`, and a counter cannot
tell a view change from an input change. A per-character signature can. It still never computes
uninvited: a character not yet calculated is named in the prompt and waits for **recalculate**.

Implementation note: it swaps the active character rather than threading one through
`sfCandidates`, `cubeCandidates` and `flameRowData`, all of which read `cur()` and the
module-level `weights`. Less surface area than a parameter on ten functions, and the
self-tests assert the active character and its weights come back untouched.

## Performance

Two memos, ~30 lines, measured rather than guessed:

| per keystroke in a star field | before | after |
|---|---|---|
| `renderRank()` (which also refreshes flames) | 616 ms | 139 ms |
| all 21 cube target scans | 167.5 ms | 2.6 ms |
| all 15 flame rows | 167.1 ms | 0.7 ms |

*(quickjs, no JIT — read these as ratios, not browser milliseconds.)*

The cause was recomputation, not slow arithmetic. `cubeCombos` was already cached, but the
**scan** on top of it — valuing every combo, grouping by threshold, running Pareto — re-ran for
all 21 cubeable slots on every render. And `renderRank()` calls `renderFlames()`, so a star-field
keystroke also rebuilt all 15 flame rows, walking a 6,618-entry distribution each. Both are now
keyed on every input they depend on, so they cannot go stale; weights are the one input the keys
omit, and a weights change clears everything.

**The Plan field only re-ranks when the effective policy changes.** Typing `444/11/44` produces
eight intermediate values — `4`, `44`, `444`, `444/` … — and none of them parse, so each falls
back to the global and leaves the policy in force *exactly as it was*. Re-ranking on them was pure
waste, and it is what made the field feel sluggish. One re-rank per word now instead of nine,
asserted in `check_js.py`. Leaving a valid plan for an invalid one *does* re-rank, because that
genuinely reverts the slot to the global. A non-empty value that doesn't parse is dimmed, since it
is otherwise silently doing nothing.

**A cache-key bug the comparison exposed.** `flameDistributionCached` keyed on seven weight
fields but the distribution reads eight — `hpFlat` was missing, so a Demon Avenger and a mage
with otherwise identical listed weights shared a wrong 6.6k-entry distribution. Latent while
only one character was ever computed per session, and reachable the moment the compare panel
started switching between them. Fixed and asserted. Fixing it also let `withCharacter` stop
clearing that cache, since the key now identifies the weights on its own.

`renderRank()` still calls `renderFlames()`. That is the safe direction — it cannot leave flames
stale — and it is now cheap.

What remains is DOM construction: `renderGear()` builds 23 rows × 13 cells from scratch, and that
is most of the residual 139 ms. **This is why a WebAssembly rewrite would not help.** WASM cannot
touch the DOM; every element still has to be created through JS, and calls crossing the WASM
boundary are typically slower than staying in JS. It would also cost the property the whole thing
is built around — no build step, opens from `file://`, every number auditable in a text editor —
and replace it with a Rust/Emscripten toolchain and an opaque binary that `selftest.html` could no
longer check. If more speed is wanted, the next targeted wins are patching gear cells in place
(as `refreshFlameRow` already does) and only building rows for the visible page.

State lives in localStorage under `maple_gear_progression`, which is per-origin: opening the
file from a different path starts fresh. Use **export** for anything you care about.
